日期：2026-09-29。状态：**用户已定向（风格化玩具感 + 方案 A Three.js）并完成 v3 P0 重做**：vendor three r158、印花月饼、跟手刀具、clipping 切割分层截面；门禁全绿、真 GPU 截图验收（详见项目 DELIVERY.md v3 节）。本文的分析、制度修复与选型结论保留作为决策记录。触发：用户第三轮否决——"无法看到全景 / 切开一点也不爽 / 画面好粗糙 / 音效难听、光影切割感都不对、体感太差 / 做不到就舍弃这个项目"。本文只做分析与决策准备，不写实现。

## 1. 取证：真实 GPU 上到底什么样（qa/gpu-probe.mjs）

用户历次看到的所有画面均出自**软件渲染**（内置浏览器合成器 / 无头 SwiftShader，1-5fps，强制降档、降分辨率、掉 AA）。为分离"美术上限"与"环境降质"，用真实 GPU（AMD Radeon, D3D11）无头 Chrome 全质量渲染并截图（`qa/output/gpu-*.png`）：

- **帧率**：2x DPR 下约 **27fps**——真实独显尚且如此，中端手机 GPU 预计 10-20fps。**爽感的前提是稳 60fps，当前栈没有这个余量**。
- **画质（全质量）**：比用户看到的明显好（裙边干净、分层正确、辉光正常），但**诚实评价仍是"技术演示"而非"美食级"**：糕点表面缺真实烤制质感（面粉、裂纹、印花浅）、流心是发光圆盘而非有厚度的稠液、刀是一块灰色板子、无景深/色彩分级/环境反射。

## 2. 归因：做不到，还是栈不对？

**两者都有，但主因是选型错误。**

| 问题 | 归因 | 性质 |
|---|---|---|
| 画面粗糙（用户视角） | ① 用户全程在软渲染环境里看（1-5fps+降档）② raymarch 全屏逐像素成本极高，无 AA/后处理余量 ③ 程序化噪声写不出食物烤制质感 | 环境+选型+美术执行 |
| 全景看不到 | v2.2 已拉远机位，但软渲染下用户仍感知差；且景深/构图层次不足以建立"全景"读感 | 部分已修，部分美术能力 |
| 切割不爽 | ① 帧率（2fps 下无手感可言）② 手势设计：刀不跟手、无连续反馈 ③ hit-stop/慢动作在低帧下变成卡顿 | 帧率+交互设计 |
| 音效难听 | 我用参数合成的"食物声"是业余水平 | 素材与方法错误 |

**技术栈判断**：手写 WebGL1 raymarching 对"精致食物 + 稳 60fps"目标是**错误选型**——每项质感提升（软阴影、环境反射、SSS、景深、泛光）都是逐像素成本的乘法，且无渲染工具链（我在字符串里盲写 GLSL，只能靠截图验证）；而栅格化网格管线（Three.js 级）这些全是开箱即用，逐像素成本低一个量级。

**美术上限判断（诚实）**：即使换栈，**本仓库约束（无外部素材渠道、ZIP≤2MiB、全程序化生成）下"照片级写实"不可达**——照片级需要真实扫描/摄影资产。可达的上限是**"精致的风格化 3D"（甜品玩具感）**。同时对照 48/49 号榜单数据：本品类头部作品本身就是**风格化/插画/玩具感**，不是照片级——"写实"最初就是被我自己拔高到最难档位的解读。

## 3. 选项与推荐

| 方案 | 内容 | 上限 | 风险 |
|---|---|---|---|
| **A. Three.js 重做·风格化甜品玩具风（推荐）** | vendor 引入 three 单文件（约 700KB，ZIP 内合法）；Lathe/圆柱几何 + PBR + 程序化 Canvas 纹理（印花/颗粒可控可迭代）+ 内置环境光 + ACES 色调映射 + 泛光/景深后处理；切割用原生 clippingPlanes；中端真机 60fps | 精致风格化 3D，接近榜单头部质感 | three r1xx 与 chrome61 目标需适配（或与总控确认放宽到实际宿主版本）；我仍是程序化美术，但有标准工具链迭代快 |
| B. 2D 插画风重做 | 高质量程序插画 + 骨骼/序列帧动画 | 榜单主流风格 | 我的程序化 2D 已被否一次（v1），无手绘资产渠道，风险高 |
| C. 放弃 26 号 | 止损，把经验写回 50 号计划（27 号敲晶洞换栈立项） | — | 沉没成本约 3 天 |
| D. 继续 raymarch 打磨 | 加倍投入当前栈 | 技术演示→勉强风格化 | 真 GPU 仅 27fps 无余量；不推荐 |

**音效（独立决策，任何方案通用）**：弃用参数合成。优先找 CC0 真实录音（切糕/奶油 ASMR 短音），ffmpeg 裁剪降噪压至 ≤60KB/段 转 Base64（符合仓库音频规则）；找不到就收敛为极简 UI 短音（不伪装 ASMR）。

**交互（任何方案通用）**：刀全程跟手（拖动即刀移动取向，松手落刀）；无效滑动给明确"未切上"反馈；60fps 为硬前提；手感参数全入 content.json。

## 4. 制度性修复（无论选哪条路）

1. **视觉验收一律先过真 GPU**：新增 qa/gpu-probe.mjs 已固化此流程；P0 评审截图必须出自真实 GPU，软渲染截图不得作为质量证据。
2. **用户过目前不自评"达标"**：两轮"门禁全绿即自我认可"的教训固化入记忆。
3. **对标先于风格解读**：任何"极致/写实"类要求，先拿榜单同类截图对齐口径再动工（本轮"写实"被拔高到照片级即源于此）。

## 5. 决策请求

需要用户拍板：① 视觉对标（风格化玩具感 vs 照片级——后者在当前约束下不可达，若坚持则建议放弃或改对标）；② 技术路线（A/B/C/D）。批准 A 后重立 P0：一只月饼的真 GPU 渲染 + 刀跟手切割 + 真实音源，过目后铺开。

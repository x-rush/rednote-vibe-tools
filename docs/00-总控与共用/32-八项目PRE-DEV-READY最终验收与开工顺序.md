## 3. 并行开发边界

用户计划让 Codex 并行承担 UI、逻辑、美术与代码。推荐每个项目内部按四条工作流并行，但采用单一契约：

- 产品/内容：只改 `src/content/content.json` 及来源记录。
- UI：只消费类型化 view model，不在组件中硬编码题目、事件和任务。
- 逻辑：纯函数优先；随机逻辑必须支持 seed；不直接依赖具体美术文件名。
- 资产：严格按 `prep/asset-manifest.json` 的 ID、尺寸槽位、许可记录生产。

合并顺序：契约与校验器 → 单条纵向切片 → 黄金样例 → 批量内容/资产 → 完整测试。四条流不得同时改同一内容 JSON；批量转写由一条专门任务负责。

## 4. 实现阶段 Definition of Done

每个项目只有同时满足以下条件才可称为“完成开发”：

1. 生产内容 JSON 通过 Schema、计数、唯一 ID、引用和安全校验。
2. 黄金路径与异常路径均有自动测试；关键玩法有确定性 seed 样本。
3. 375、390、430 像素宽度无横向溢出，44px 级主要触控区可用。
4. 首次离线启动成功；刷新、退后台、存储损坏不白屏。
5. 不发送业务数据到后端，不包含运行时外部 API，不保存用户图片。
6. 资产有来源/生成记录，包体和图片尺寸经过压缩检查。
7. 分享卡不泄露用户未选择公开的内容；对话复盘默认无痕。
8. 比赛提交当日重新核对官方规则、构建方式、包体与审核要求。

## 5. 已知但不阻塞开工的后续门禁

- 文物馆藏页可能更新；发布前做一次链接与文字复查，首发图片默认原创/AI 示意重绘以避开授权依赖。
- 大理寺是受古代文字文化启发的虚构案件；涉及真实字源时才需要逐条引用，剧情不伪称史实。
- 饮子铺的价格、成本、事件概率是游戏经济而非历史统计；需在实现后通过 seed 模拟调参。
- 比赛页面和小工具规范具有时效性；提交前必须重新联网核验。

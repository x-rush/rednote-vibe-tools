# 花少有狼：需求趣味性与纯前端审计

日期：2026-09-15。
审计对象：当前 REQUIREMENTS.md 与 content.json 的已整理需求及内容，基于本轮已掌握版本。
阶段：开发前文档审计。没有游戏实现，不是代码审计、性能测试或实测可玩性结论。
产品名已由用户确认改为「花少有狼」。下列玩法修订为审计建议，不自动视为用户批准扩展范围。

## 结论

纯前端方向成立：七席本地规则模拟、随机身份、条件化台词、状态存档均可在浏览器本地完成。
当前需求有可玩骨架，但趣味尚未闭环：最大风险是玩家长时间看电脑说台词，而自己的行动没有明确可观察后果。
新季与化名能吸引第一次点击，但持续游玩的理由必须来自读懂矛盾、影响站队、身份变化及复盘。
建议收紧为七人单人局，以「公开证据 -> 玩家选择 -> 角色回应 -> 票型改变」作为核心闭环。
不建议靠堆叠更多通用金句、身份技能、装饰页面来弥补核心交互。
以下严重度按对第一版体验与交付的影响排序，不代表已在代码中发现故障。

## 发现 1 [P1] 玩家发言对电脑投票的影响未定义

依据：需求已有质疑、支持、辩护和声称身份按钮，但没有明确这些操作改变哪个决策状态，以及玩家如何感知变化。
后果：界面有按钮却只是换一句台词，玩家无法判断自己是否做对，也难以产生翻盘体验。
建议：主要发言由「行动 + 目标 + 可选公开证据」组成。证据来自系统可核实事件，例如前后表态或票型不一致。
建议：电脑对证据作出回应，并在自己的信任/怀疑状态中产生有上限的变化；最后投票可受其影响，但不保证固定转票。
建议：无证据的试探也允许，但不获得与有效证据相同的权重；重复点击同一论点不能累积收益。
验收：在固定随机种子的同局分支中，有效质疑与跳过能在至少部分合理情境产生不同回应或票型；不能所有人对任何质疑一律跟票。
验收：反馈展示公开态度变化，不显示内部怀疑分数或隐藏阵营。

## 发现 2 [P1] 六位角色先说完再由玩家发言，互动可能退化为末位操作

依据：现有主流程把六位发言安排在玩家选择之前。
后果：电脑本轮已经发完言，玩家质疑没有及时回声，容易变成看完文本再点一票。
建议：日间拆成简短首轮发言 -> 玩家一次主要行动 -> 被点名角色和一位相关角色回应 -> 投票。
建议：并非每次都让六位再次讲话，只显示因当前行动触发的必要回应；支持逐条、快进和查看历史。
验收：一轮玩家行动后至少出现目标相关回应；若玩家跳过，则可以直接投票。
验收：玩家被点名时有辩护入口，不必被动等到整轮结束。

## 发现 3 [P1] 当前 42 条样本不足以让角色推理，也不足以支撑重复游玩

依据：台词主要为无目标幽默句；质疑句仅有笼统的 matching-public-evidence 条件，没有结构化证据类型与变量绑定。
后果：随机播放可能虚构投票矛盾；扩写到 168 条仍可能只是同一种话的变体。
建议：先拆为证据句、身份声称句和角色口吻句三层，再扩量。
建议：证据模板包含公开事件 ID、目标、轮次；声称身份与引擎真相分别存储；纯口吻句不得无条件包含事实断言。
建议：没有证据时使用明确的试探表达，不声称对方前后矛盾。
例：证据句描述「第 1 天声称支持 3 号，最终却投给 3 号」，再附加一条角色口吻句。
验收：每个事实型输出都可追溯到允许读取的事件；狼人编造的查验必须标为声称，不写入真实查验历史。
建议：优先完成 12 个典型局势的可用内容包，再将总语料扩至 168 条。数量是覆盖目标，不是趣味验收标准。

## 发现 4 [P1] 电脑规则描述不足以保证推理感、公平性和局势变化

依据：已有观察视图与禁上帝视角约束，但未定义证据可信度、预言家身份冲突、跟票动机与首次无信息决策。
后果：过度随机则无法推理；权重固定则几局就被看穿；读取真相则不公平。
建议：以公开观察、合法私密信息和有界随机扰动决策，策略状态与嘉宾风格分离。
建议：先覆盖无证据开场、单预言家声称、双预言家冲突、被质疑、狼队友被投和残局等情境。
建议：计算票型理由而不是事后编造理由，允许概率判断失误，不保证真预言家自动被信任。
验收：相同观察视图与相同随机输入下，改变代理不可见的真相不得改变其行动；改变合法可见证据则可改变其行动。
验收：复盘说明公开证据和实际动作，不把引擎真相伪装成电脑当时已经知道的信息。

## 发现 5 [P2] 首夜淘汰与等待可能破坏新用户体验

依据：玩家随机身份，可能第一夜死亡；目标时长 10～20 分钟，但没有阅读量、响应等待及死亡后的实际节奏标准。
后果：用户尚未参与就只剩旁观；移动端读六个人长发言容易退出。
建议：默认对局保留正常规则，不暗中免死或操纵抽牌。另提供可选固定教学局，明确与随机正式局区分。
建议：常规发言默认一到两句，可展开证据；所有模拟等待可快进。
建议：出局后提供立即重开和快进复盘，查看全身份需要进入明确结束/放弃当前玩家参与的复盘状态。
验收：首次开局无强制长动画；出局后不要求读完全部发言才能退出。
待试玩确认：10～20 分钟是否过长，先以实际首局完成率和阅读节奏调整，不先承诺缩短到某个实测数字。

## 发现 6 [P2] 化名和头像的追综识别度尚未成立

依据：名称多为临时谐音；头像未经逐张审核且未核对本季公开造型，王可采用泛化年轻旅行者描述。
后果：可能被看作七张普通旅行卡，新季热点只能体现在标题上。
建议：名称按辨识度、顺口度、趣味、非恶意四项筛选，保留候选而非直接定稿。
建议：每人补一张公开视觉参考来源和一个本季可核实的元素。不要把生成图当作事实参考。
建议：在不显示原名的情况下做小样识别评审；未识别出来时优先改名/轮廓，不靠增加长说明。
验收：每张角色卡的真实素材依据与原创部分有清楚研究记录；前台文案不把创作称作节目原话。
说明：本次未对七张候选进行视觉审计，不能据此宣布合格。

## 发现 7 [P2] 复盘未明确给出第二局的动机

依据：当前复盘只有身份、关键票型和趣味发言，缺少与玩家选择的关联。
后果：输赢只是一张结果页，用户不知道自己在哪一步看错或说服了谁。
建议：展示玩家身份、关键选择、与该选择有关的实际回应/票型，以及一条基于历史的回顾。
建议：不能凭空声称「你改变了三个人的投票」，除非引擎记录了可支持的变化；没有因果证据时只描述先后事实。
建议：提供再来一局，允许系统独立重新抽卡，不强制换身份伪造随机。
验收：结算短文由真实事件生成，不随机颁发与对局无关的高光称号。

## 纯前端可行性

| 能力 | 本地实现方式 | 必要边界 |
| --- | --- | --- |
| 嘉宾和身份独立随机 | 浏览器 JS 洗牌，两套独立随机过程 | 同局不重复，身份配额正确 |
| 六位电脑决策 | 本地状态机、观察视图、证据权重与有界随机 | 无需外部模型；不承诺自由聊天 |
| 发言与金句 | 本地 JSON 模板、事件绑定、场景选择 | 事实条件校验，避免机械随机 |
| 日夜、技能、投票和胜负 | 本地游戏状态机 | 夜间整批结算，防重复操作 |
| 结构化存档 | localStorage / IndexedDB | 版本校验，不保存媒体/Base64/Blob |
| 头像展示 | 随静态构建打包的 PNG/WebP 等文件 | 不从外部图片站或运行时 CDN 拉取 |
| 结果卡 | HTML/CSS 可截图页面 | 第一版不依赖文件下载、剪贴板或分享设备 API |
| 新季内容更新 | 人工维护 content.json 并重新静态发布 | 不是运行时自动追踪热点 |

判定：可以是完整的纯前端项目，而不只是前端壳。
构建/检查命令使用 Node 不等于游戏运行依赖 Node；线上仅需静态托管。
生成头像时使用图像生成工具属于研发阶段，不属于玩家运行时依赖。
研究网页用于资料核验，不是游戏必须联网调用的数据源。
纯前端含义不等于双击 file:// 必须可用；入口通常是静态 HTTP(S) 页面，JSON 需通过构建打包或同源静态加载。
无 Service Worker 时不承诺关闭页面后还能无网络重新打开；加载完所需静态资源后，对局本身无需外部服务。
单人本地隐藏信息隔离是代码设计约束，不是对拥有浏览器开发工具的玩家提供防作弊安全保证。
没有实际代码和构建产物，因此以上是架构可行性结论，不是已验证零外部请求。

## 建议的第一版范围

保留：七张角色卡、双随机、一个七人规则配置、结构化发言、证据回应、投票、结算复盘、存档恢复。
优先补：12 个典型局势内容包、代理合法观察边界、玩家行动反馈、化名和头像识别。
暂缓：真人聚会、联网房间、自由聊天、角色专属技能、更多神职、复杂评分体系、自动抓取实时节目内容。
可选：固定教学局，作为独立明确模式，不暗改普通局规则。

## 进入开发前的放行标准

- 明确一轮日间发言的交互顺序与玩家一次行动如何触发回应。
- 至少写出 3 个完整可读的样局片段：平民有效质疑、预言家被反跳、狼人被怀疑后辩护。
- 确定七个名称，补视觉参考并完成候选头像评审。
- 核心规则与事实型模板条件无歧义；明确弃票/平票/夜间同时死亡等情况。
- 开发后按项目规则执行 pnpm lint、pnpm test、pnpm build，以及 375/390/430 px 和非零安全区验证。
本轮只审计需求，未执行不存在的游戏构建或试玩，不以纸面评分替代用户试玩。

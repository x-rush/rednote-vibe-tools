# 汴京饮子铺：完整剧情与事件系统重构规格

状态：待用户书面复核

日期：2026-08-26

范围：仅 `projects/04-bianjing-drink-shop`

## 1. 目标

把当前可运行但仍带有内部缩写、模板正文和无效长期状态的事件骨架，重构为可正式交付的“市井温情＋真实经营取舍”内容系统。

本轮保留以下产品框架：

- 一局经营 100 日；
- 80 个普通事件，仍按八类、每类十个组织；
- 5 条连锁，每条由入口和三个后续节点组成；
- 8 个结局；
- 每日最多处理一个主要事件；
- 固定 seed、纯前端、本地结构化存档；
- 不新增后端、运行时 CDN、外部 API、Service Worker 或必要设备权限。

允许合理调整事件数值、结局阈值与长期效果，但不能静默改变基础备货、定价和随机数的确定性契约。所有业务正文继续只存在于 `src/content/content.json`。

## 2. 内容原则

### 2.1 叙事基调

- 以普通经营者、街坊、来客和供货人的日常处境为核心；
- 温情不等于善意永远最优，逐利也不写成品德缺陷；
- 每个选择至少有一种清楚收益和一种真实代价；
- 语言自然、克制、易读，可以有轻微幽默，不使用密集古语或现代网络梗；
- 历史环境是创意重构，不声称人物、器物或饮品为精确历史复原。

### 2.2 信息透明度

选择前：

- 明确当下影响方向，例如“需要额外投入”“会消耗体力”“有利于口碑”；
- 不显示精确数字；
- 长期影响只提示“可能留下后续”“日后成本或有变化”等悬念；
- 不展示 `M / R / E / H / F / X / C`、内部 flag、modifier ID 或未来节点名。

选择确认后：

- 展示一段与行动直接对应的结果短文；
- 展示资金、口碑、体力、人情的精确变化；
- 展示已经生效的长期状态及期限，但不泄露尚未发生的剧情；
- 连锁只显示故事名和“留下新线索／故事暂歇／故事收束”。

### 2.3 单事件结构

每个普通事件必须包含：

1. 具体标题；
2. 两至四句场景正文，说明人物、现场与难处；
3. `opening / business / closing` 三种时段之一；
4. 场景位置和角色类型；
5. 日期、天气、季节或经营状态条件；
6. 两个行动明确、立场均合理的选项；
7. 每个选项一至三条中文定性提示；
8. 每个选项一段确认结果；
9. 与提示一致的即时效果；
10. 如有长期效果，必须存在真实消费者或后续节点。

禁止继续使用“`{标题}摆在柜前，你要如何应对？`”模板。

## 3. 八类事件的内容职责

| 类别 | 数量 | 主要时段 | 内容职责 |
|---|---:|---|---|
| 日常经营 | 10 | opening / business / closing | 器具、排队、找零、卫生和账目 |
| 天气时令 | 10 | opening / business | 菜单适配、临时损耗和季节机会 |
| 顾客故事 | 10 | business | 熟客、旅人、孩子、书生与劳动者 |
| 市场供应 | 10 | opening / closing | 供货关系、价格、质量和库存风险 |
| 身心状态 | 10 | opening / closing | 休息、疲劳、学习和经营节奏 |
| 邻里人情 | 10 | business / closing | 互助、边界、公平和社区责任 |
| 风险麻烦 | 10 | opening / business / closing | 修缮、谣言、坏钱、债务和安全 |
| 机会成长 | 10 | opening / closing | 扩店、配方、学徒、灯会和招牌饮子 |

天气类事件必须有实际天气或季节条件；普通事件可以只使用日期和经营状态，但不能靠类别名假装条件已经生效。

## 4. 五条连锁剧情

### 4.1 通用结构

每条连锁由普通事件中的一个入口选择启动。入口本身就是故事第一幕，不再在下一日重复同一场景。随后依次进入三个新节点：

1. 发展：入口选择产生第一次回声；
2. 转折：出现新的经营或人物矛盾；
3. 收束：根据前两次选择和经营状态形成至少两种结果。

每个节点声明最早和最晚触发间隔。超时必须有符合剧情的中断文案，不能只保存 `timeout`。

### 4.2 一碗换一诗

- 入口：是否让暂时手紧的诗人赊饮；
- 发展：街头出现未经许可的传唱，决定放任传播或说明店名归属；
- 转折：诗人归来，能以钱、题名或人情偿还，但各有代价；
- 收束：形成“清账”“题名留念”或“好意无回声”的结尾。

### 4.3 灯下百杯

- 入口：是否报名灯会临时摊位；
- 发展：根据本金决定保守或充足备货；
- 转折：灯会骤忙时选择限量稳定或追加产量；
- 收束：综合销量、损耗、体力和口碑结算，不保证报名必赚。

### 4.4 半个学徒

- 入口：是否试用前来求学的少年；
- 发展：选择先教卫生流程或先教待客；
- 转折：学徒犯错后选择公开指出或一起补救；
- 收束：留下会减少后期体力但增加工资，推荐他处则获得人情并结束师徒关系。

### 4.5 一纸大单

- 入口：是否承接公门小宴订单；
- 发展：原料不足时选择高价补货或主动缩减品类；
- 转折：交付前发现品质与数量不可兼得；
- 收束：准时、品质和账目共同决定利润与口碑，不把公门订单写成无条件奖励。

### 4.6 招牌饮子

- 入口：选择现有饮子作为招牌，或投入研发新品；
- 发展：确定清爽、温暖或草木香的研发方向；
- 转折：三类顾客给出互相矛盾的反馈，选择稳定核心或继续调整；
- 收束：形成大众畅销、口碑小众或研发过度三种结果，并真正影响商品解锁和后续需求。

## 5. 内容数据契约

### 5.1 事件呈现字段

普通事件和连锁节点共同提供以下呈现数据：

```ts
type EventTiming = 'opening' | 'business' | 'closing'

type EventActorRole =
  | 'none'
  | 'worker'
  | 'merchant'
  | 'scholar'
  | 'youth'
  | 'elder'
  | 'neighbor-woman'
  | 'runner'

type EventScene = {
  timing: EventTiming
  location: 'counter' | 'street' | 'kitchen' | 'market' | 'back-room'
  actorRole: EventActorRole
}

type ImpactHint = {
  axis: 'money' | 'reputation' | 'energy' | 'relationships' | 'inventory' | 'future'
  direction: 'up' | 'down' | 'mixed' | 'uncertain'
  text: string
}

type EventChoice = {
  choiceId: string
  text: string
  impactHints: ImpactHint[]
  resultText: string
  effects: EventEffect[]
}
```

`impactHints` 是业务内容，不由 JSX 拼字。引擎校验确定性资金和状态效果与提示方向一致；`future / uncertain` 只用于 flag、延期效果、连锁或波动 modifier。

### 5.2 条件字段

在现有日期、状态、flag 和链状态条件上增加：

```ts
type ContextCondition =
  | { type: 'weather-is'; weatherId: string }
  | { type: 'weather-in'; weatherIds: string[] }
  | { type: 'season-is'; seasonId: string }
  | { type: 'season-in'; seasonIds: string[] }
```

事件候选过滤同时接收 `GameState` 与当日 `DayContext`。天气事件不得只靠标题表达天气。

### 5.3 长期效果

`set-modifier` 不再依赖引擎硬编码少数 ID，而是保存可通用消费的目标：

```ts
type ModifierTarget =
  | 'visitor-count'
  | 'energy-cost'
  | 'fixed-cost'
  | 'sales-income'
  | 'waste-return'
  | 'product-demand'

type SetModifierEffect = {
  type: 'set-modifier'
  modifierId: string
  target: ModifierTarget
  operation: 'add' | 'multiply'
  value: number
  durationDays: number
  productId?: string
  playerLabel: string
}
```

活动 modifier 由经济引擎按 `target / operation` 统一计算。每个 `add-flag` 必须至少被某个事件条件、连锁分支或结局条件读取；否则内容校验失败。

### 5.4 结果快照

`DailyResult` 增加只由 ID 和数值组成的事件结果摘要：

```ts
type EventResolution = {
  eventId: string
  choiceId: string
  moneyDelta: number
  statDeltas: Partial<Record<ShopStatKey, number>>
  activatedModifierIds: string[]
  chainId?: string
  chainStatus?: 'active' | 'completed' | 'interrupted'
}
```

结果正文从当前内容版本按 `eventId / choiceId` 映射，不把整段业务文案写进存档。

## 6. 每日引擎流程

### 6.1 生成当日计划

`openDay` 调整为只完成以下工作：

1. 校验备货、售价和体力；
2. 固定天气、季节和候选事件；
3. 以纯函数计算基础营业结果，将销量、账目和体力成本作为不可变计划写入 `PendingOpening`；
4. 保存安全快照；
5. 不提前修改资金、体力、库存或日期。

营业计划只计算一次，事件选择不得触发第二次销量随机。UI 可以按阶段播放计划中的销量，但 HUD 只显示已经提交的状态，不能提前写入尚未结算的收入。

普通事件的当日交易影响使用独立事件账目行表达，例如“临时添料”与“额外售出”，不重算基础销量。新增长期 modifier 统一从下一日生效，避免选项确认前后改变已经播放的营业事实。

### 6.2 按时段展示

- `opening`：开门清单后、营业流水前出现；
- `business`：先展示不含精确销量的市声片段，再进入事件；
- `closing`：完整营业流水后出现；
- 无事件：营业流水结束后直接日结。

营业流水只播放已经固定的表现阶段，不允许重复计算经济结果。

### 6.3 原子结算

`resolveDay` 接收已确认的 `choiceId`：

1. 读取 `PendingOpening` 中唯一的基础营业计划；
2. 应用备货、销量、损耗、固定成本、体力和事件专属账目；
3. 应用普通事件或连锁效果；
4. 生成 `EventResolution` 和逐笔账；
5. 清除 pending day、推进日期并持久化；
6. 使用 `resolutionId` 保证双击和恢复重放都只结算一次。

## 7. 玩家界面

### 7.1 事件三态

1. 情境态：时段、地点、人物、两至四句正文、两个选项；
2. 待确认态：选中项展示中文影响提示和“确认前仍可更换”；
3. 已发生态：展示结果短文、精确变化和已生效长期状态，再进入营业或日结。

### 7.2 日结反馈

账簿新增事件专节：

- 事件标题；
- 玩家所选行动；
- 对应结果短文；
- 资金与三项状态变化；
- modifier 的玩家可懂名称和剩余日数；
- 连锁故事进度。

不再把所有事件钱款都压缩成同名“今日事件影响”。

### 7.3 角色与场景

现有劳动者、掌事和士人继续复用。新增四张透明角色基准：

- 少年；
- 老客；
- 街坊妇人；
- 差役或公门跑腿。

器具、账目、天气和店铺维护事件允许 `actorRole: none`，使用店铺场景、天气层和代码原生类别符号，不能强行放入不相干人物。

## 8. 数值重平衡

### 8.1 单次效果范围

- 小变化：资金或状态 `2–4`；
- 中变化：`5–8`；
- 大变化：`9–15`，只用于一次性、链入口或明显高风险节点；
- 普通可重复事件不能让单一选择长期形成无条件正收益；
- 同一事件两个选项若影响相同维度，至少一个维度的方向、确定性或期限必须不同。

### 8.2 长期效果约束

- 正向 modifier 必须有前置成本、期限或条件；
- 风险 flag 必须有实际触发机会、解除方式或结局读取；
- 延期扣款必须在选择前提示“日后仍有支出”；
- 任何“增加销量／降低成本／保护体力／增加容量”都必须进入真实计算或被改写为不承诺该效果的文案。

### 8.3 模拟验收

执行五类策略代理，每类 200 个固定 seed，共 1,000 局：

- 每类策略至少存在成功活到第 100 日的样本；
- 总体破产率保持在 `5%–45%`，避免无风险或随机暴毙；
- 任一策略的单一特色结局占比不得超过 `80%`；
- 第 100 日资金中位数不得超过 `2,500` 文；
- 体力为 0 的终局比例不得超过 `30%`；
- 同一 seed 和策略必须得到完全一致终态。

八个结局另用明确构造场景验证可达，不依赖概率碰撞。

## 9. 存档版本与迁移

存档 schema 与 content version 提升到 V2。

### 9.1 保留内容

- 已完成日数；
- 资金、口碑、体力、人情；
- 库存、价格、解锁饮子；
- 已完成事件历史；
- 已解锁结局。

### 9.2 未结算当日

旧存档存在 `pendingOpening` 时恢复 `previousDay` 安全快照。若上一日快照不可用，进入明确的恢复错误页，不尝试猜测或反算已经提前写入的营业收入。

### 9.3 旧连锁状态

- `nodeIndex >= 0` 的真实进度按节点 ID 映射并保留；
- `nodeIndex === -1` 且入口已确认的状态迁移为已完成入口、等待后续发展节点；
- 因旧 bug 产生、尚未进入后续节点的 `timeout` 同样恢复为等待发展节点；
- 已完成或带有明确玩家选择导致的中断继续保留；
- 迁移后把 `lastAdvancedDay` 设为迁移当日，避免刚恢复即再次超时。

### 9.4 旧长期状态

已知 modifier 映射到新通用 target。没有实际消费者的旧内部 flag 和 modifier 不进入 V2 活动效果，但迁移日志保留其 ID，界面只提示“已清理旧版未生效状态”，不展示内部名称。

## 10. 内容与代码校验

生产内容校验新增以下硬门禁：

- 恰好 80 个普通事件、5 条连锁、每链 3 个后续节点、8 个结局；
- 普通事件正文不等于标题模板，且达到最低有效长度；
- 190 个事件与连锁选项均有 `impactHints` 和 `resultText`；
- 提示文本不得为单字母内部代码；
- 确定性资金与状态效果必须和提示方向一致；
- 天气类事件至少有一个天气或季节条件；
- 所有角色、天气、季节、商品、chain 和 modifier 引用有效；
- 每个新增 flag 至少有一个消费者；
- 所有 modifier target 均被经济引擎支持；
- 事件和链结果不得含远程 URL、Base64、Blob 或媒体数据。

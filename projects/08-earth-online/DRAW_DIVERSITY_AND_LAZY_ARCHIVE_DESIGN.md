# 地球 Online：抽取多样性与旧档案按需加载设计

日期：2026-08-29
状态：待产品最终确认

## 背景

本轮解决两个相关但不同的问题：

1. 当前匹配器只强排除最近 3 次推荐；相同偏好会形成较小的 exact 候选池，因此任务可能较快重复。
2. 为保证旧进行中任务按原步骤和原 XP 完成，当前主包同步包含 20 个退役定义和 80 个同 ID v1 定义，使标准构建 JS 原始体积达到 627.00 kB、gzip 120.50 kB。

内容源继续只有 `src/content/content.json`，不新增依赖、后端、网络 API、定位或上传能力。

## 当前重复原因

用户偏好会直接缩小候选池：

- 时间和精力是上限；exact 阶段又优先要求精力等级相同。
- 目标必须在 exact 阶段一致。
- 室内/户外、昼夜、熟悉地点和社交边界均为硬条件。
- 5 分钟、E1、室内、不社交通常形成最窄候选池。
- 当前只把最近 3 个任务从 clean 候选中排除。
- exact 池耗尽后进入 `recent-relaxed`，当前所有近期任务受到相同待遇，可能较快抽回刚见过的任务。
- 类别疲劳只检查上一条历史类别，力度为 -10；未接受的普通 offer 不形成充分的类别记忆。

安全、时间上限、精力上限、环境、地点、社交、预算和不适用条件不是重复问题的可放宽手段。

## 抽取多样性设计

第一阶段不引入持久化 shuffle bag，不升级 Storage Schema。复用现有最多 10 个 `recentQuestIds`：

1. clean 阶段的近期强排除窗口由 3 扩为 8。
2. 评分加入位置相关的近期衰减：越接近最近一次推荐，惩罚越高；时间越久惩罚逐步降低。
3. 根据最近推荐 ID 推导类别，对最近 4 次出现的同类任务施加可累计类别疲劳惩罚。
4. 高适配随机带由最高分向下 15 分扩大到 25 分，让更多仍然合适的任务参与 seeded 加权选择。
5. `recent-relaxed` 阶段不再把所有近期任务等价处理；优先最久未出现的候选，最后才允许最近任务回归。
6. 推荐解释在因多样性选中任务时增加“近期没有出现过”或“换了一类冒险”的本地文案。

保证：

- 若同一阶段存在至少 8 个合法候选，连续推荐期间不会在前 8 次内重复任务。
- 候选不足时按“最久未出现”轮换，不保证凭空制造不存在的候选。
- 相同偏好、任务库、历史和 seed 仍产生相同结果。
- 安全及用户明确条件永不放宽。
- 完成冷却和近 7 天放弃规则继续保留。

如果上线后仍需“整个候选池抽完前绝不重复”，再单独设计 preference-specific shuffle bag；本轮不提前增加 Schema 和迁移复杂度。

## 旧档案按需加载设计

### 单一内容源

`src/content/content.json` 继续保存全部 active、retired 和 legacy 定义。项目内 Vite 插件在开发/构建时读取该文件并提供三个虚拟模块：

- current content：包元数据、UI、100 个 active，退役与 legacy 数组为空。
- archive content：20 个 retired 和 80 个 legacy。
- archive loader：标准 Web 构建使用动态导入；小程序构建使用静态 eager 导入。

不生成需要提交的内容副本，不在运行时请求外部 URL。

### 启动流程

1. 同步加载 current content 并验证 100 个 active。
2. 只读取 localStorage envelope 的最小结构，判断是否需要旧档案。
3. 以下情况加载 archive chunk：
   - Schema v1 需要历史或活动任务迁移；
   - v2 活动任务的 ID/版本不属于当前 active；
   - v2 `completedQuestIds` 包含当前 active 中不存在的旧 ID。
4. 合并 archive 后创建完整 `QuestCatalog`，再调用现有 `loadState`。
5. 干净用户和只引用当前任务的正常 v2 用户不加载 archive。
6. archive chunk 加载或校验失败时进入现有内容恢复页面，不丢弃或覆盖原 localStorage。

### 小程序构建

`vite.minitool.config.ts` 使用同一插件的 eager 模式，把 archive 内联到唯一 IIFE。小程序包继续满足单 HTML、单经典 JS、无动态 import、无 fetch 的既有校验。标准 Web 构建才使用独立本地 archive chunk。

## 接口调整

- `App` 改为接收已经准备好的 content/catalog，不再在模块顶层同步导入完整 JSON。
- 新增纯函数检查存储是否需要 archive；损坏 JSON 和未来版本不触发无意义加载。
- 新增异步 bootstrap：准备 current catalog，必要时加载 archive，再渲染应用。
- `createQuestCatalog` 和领域结算规则不改变；只有输入内容由 bootstrap 决定是否含 archive。
- 内容生产校验继续针对完整 `content.json`；运行时 current 校验允许空 archive，但仍严格校验 100 个 active。

## 测试

抽取多样性：

- 至少 8 个合法候选时连续 8 次不重复。
- recent 窗口耗尽时优先最久未出现任务。
- 最近 4 次类别疲劳能改变同分候选顺序。
- 同 seed、偏好和历史可复现。
- 无多样性策略可以突破安全、时间、精力、环境、社交或预算硬条件。
- 候选不足时放宽解释正确。

按需加载：

- 空存储、当前 v2 存储不请求 archive loader。
- v1、旧版 active、旧 completed ID 请求 archive。
- archive 加载后旧任务仍显示原标题、步骤和 XP。
- archive 加载失败保留原存储并进入恢复状态。
- 标准 build 产生独立 archive chunk，主 chunk 不包含 legacy 标题样本。
- 小程序 build/validate 仍是单 JS 且通过禁止能力扫描。

最终运行 `pnpm lint`、`pnpm test`、`pnpm build`，并额外运行项目已有的 `pnpm build:minitool` 与 `pnpm validate:minitool`。浏览器验证干净用户不请求 archive、v1 用户请求 archive，以及 375/390/430px 和非零安全区。

## 验收标准

- 普通用户的标准 Web 主 chunk 不再包含 80 个 legacy 定义，并消除当前 500 kB 主 chunk 提示。
- v1 用户仍按旧定义和旧 XP 完成任务。
- 同一偏好在候选充足时前 8 次不重复，候选不足时遵循最久未出现轮换。
- seed 可复现且所有安全硬条件不变。
- `content.json` 保持唯一业务内容源，无新增依赖或共享文件修改。

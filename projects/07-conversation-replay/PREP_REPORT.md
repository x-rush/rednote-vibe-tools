## 2. 情境筛选与匹配规则

所有算法为纯函数，不使用随机、在线模型、自由文本或隐藏分析。

基础筛选函数：

1. 按 `relationshipType` 筛选关系。
2. 按 `communicationGoalIds` 筛选沟通目标。
3. 按 `conflictLevel` 筛选冲突程度。
4. 用 `emotionId` 与 `originalExpressionId` 匹配情境风险和原表达风险，并用 `responseId` 匹配对方可观察反应。
5. 每个候选按整数权重评分：关系 16、目标 8、冲突程度 4、情绪 2、原表达 2、对方反应 1；仅在同分时按稳定 `scenarioId` 字典序决胜。
6. 用户明确选择具体情境时使用该情境，但 `conflictLevel=safety` 拥有更高优先级，不能被具体情境绕过。

## 3. Fallback 顺序

无精确匹配时按以下固定顺序放宽条件，并在结果中返回匹配层级和原因：

1. `exact`：关系 + 目标 + 冲突程度 + 情绪 + 原表达 + 对方反应。
2. `response-relaxed`：关系 + 目标 + 冲突程度 + 情绪 + 原表达。
3. `emotion-relaxed`：关系 + 目标 + 冲突程度 + 原表达。
4. `conflict-relaxed`：关系 + 目标 + 原表达。
5. `relationship-goal`：关系 + 目标。
6. `goal-only`：只保留目标。
7. `general`：通用且安全的复盘结构；若内容包异常为空则抛出可恢复错误，不返回空白页。

## 4. 内容安全边界

- 不判断谁对谁错，不推断人格、疾病或对方动机。
- 不生成报复、羞辱、控制、威胁或情感勒索建议。
- 不暗示所有冲突源于用户表达方式，也不保证换种说法就能修复关系。
- 身体同意情境被标记为 `safety`，拒绝立即生效，不要求用户用更温和的话解释后才有效。
- 暴力、威胁、跟踪、强迫、严重控制、监控、经济控制、隔离、自伤/他伤或立即危险统一使用通用安全 fallback：先离开可能升级的现场，联系可信任的人，并按所在地实际情况寻求紧急或专业支持。
- 安全结果不复用某个普通关系或身体边界案例的标题和改写；其三语气、结构、下一步和分享摘要都来自独立安全 fallback。
- 安全结果明确写出“不必独自对质”，普通沟通技巧不会作为唯一答案。
- 不硬编码可能过期的紧急电话号码，不提供高风险专业诊断。

## 5. ReplayResult 与复盘卡 ViewModel

`ReplayResult` 提供：

- 命中情境与可解释匹配层级。
- 原表达风险。
- 更适合的表达结构。
- 柔和、直接、坚定边界三版表达。
- “现在可以怎样补一句”。
- “下次可以怎样说”。
- 可执行下一步。
- 复盘总结、分享摘要和内容版本。
- 安全情境的固定安全提示。

`ReplayCardViewModel` 只提供页面展示需要的数据：标题、五个复盘区块、三张语气卡、下一步动作、安全提示和分享摘要。React 组件不直接解释匹配规则，也不读取情境内部引用关系。

## 7. 存储 Schema

localStorage key：`xhs-tool:conversation-replay:state:v1`。

```text
schemaVersion: 1
contentVersion: string
updatedAt: ISO 8601
data:
  saveMode: ephemeral | local
  draft?: Partial<ReplayAnswers>
  recentResult?: StoredReplay
  savedResults: StoredReplay[]  // 读取与写入都限制为最近 3 条
```

主动保存历史使用原生 IndexedDB：

```text
database: xhs_say_it_again
store: debriefs
keyPath: id
limit: 最近 3 条
```

存储只包含选项 ID、情境 ID、时间和版本，不保存聊天记录、截图、图片、Base64、音视频或 Blob。读写边界均递归拒绝媒体字段和 `data:`/`blob:` 数据，并校验枚举、内容引用、ISO 时间与未知字段。恢复流程处理非法 JSON、截断数据、未来 schema、旧内容版本、失效引用和超量数组；失败时返回安全默认值，不静默覆盖未来版本数据。本地模式会立即持久化模式选择，刷新后恢复到首个未完成步骤；重新复盘会清除旧草稿但保留本地模式。

第 4 次主动保存前会显示将被替换的最早记录及时间，用户可以取消；历史页也支持逐条确认删除。IndexedDB 仍在写入层执行最多 3 条的最终上限。

# E07 评测与调试

正式提问仅展示场景和问题，锚点用于内部校准。

## Q21 测试与模块边界

能力 E07；前提：知道该模块的输入输出；没有生产经验可按题面假设回答，语言与框架不限定。

场景：假设一个函数同时检索、调用模型和写订单；当前只有“成功提交”测试。禁止测试触发真实付款，外部响应可用替身。

问题：把模型调用、检索和业务规则写在一个函数里后测试很困难。你如何拆分，并证明失败路径也被覆盖？

- 若只有成功路径时：模型返回非法结构时，哪一层负责拒绝？
  - 期待证据：能给非法输出时执行次数为零的断言，以及响应丢失后的幂等测试。
- 若已讲清核心流程但缺少可验证证据：请给出一个能检验“测试与模块边界”方案是否有效的失败样例和预期结果。
  - 期待证据：能给非法输出时执行次数为零的断言，以及响应丢失后的幂等测试。 需要明确失败输入、预期终态和可观察断言，不能仅列工具名称。
- 若自报已经在项目中实现：在你负责的部分，“测试与模块边界”具体有什么输入、输出和可提供的证据？没有资料也可以说明限制。
  - 期待证据：能给非法输出时执行次数为零的断言，以及响应丢失后的幂等测试。 还需区分本人实现与团队结果，给输入输出或脱敏材料；未提供材料只记自报，不声称核实。

最低合格：纯规则/外部适配/写入分层；高危失败路径与零调用断言；mock不替代契约测试

- 未体现：未回答核心问题，或坚持“mock测试通过就是线上可靠”且无法解释；只记录当前答案缺口。
- 基础理解：能解释纯逻辑与外部适配边界，但尚未把情景处理流程说清。
- 可应用：能结合题目说明纯逻辑与外部适配边界和可替换依赖和真实契约，给出可执行处理。
- 较完整：在可应用基础上覆盖失败、边界及少量集成测试，给出验证方法并解释取舍。

### Q21-V1

原创假设：退款金额10元，订单真实存在但属于其他用户，禁止真实支付测试。

模型返回合法JSON但用户ID越权，pytest全绿；你会把哪个测试加在哪一层来保证退款函数不被调用？

期待证据：业务授权拒绝与退款调用次数零的断言。

课程补练 E07：列出模块输入输出及五个高价值测试

## Q22 任务评估集

能力 E07；前提：知道该模块的输入输出；没有生产经验可按题面假设回答，语言与框架不限定。

场景：假设退款问答Agent有100条评测：70可回答、20证据不足、10越权攻击；单任务最长8步。需报告任务成功率、成本和p95。

问题：团队凭几个演示宣布客服Agent可上线，你如何设计实习生也能维护的评估集？

- 若自信地以少量全对或模型自评宣布上线时：10条攻击都通过、模型自评分很高，是否足以证明安全和任务成功？你还要核对什么实际结果？
  - 期待证据：有限样本不能证明零风险；核验业务终态，独立保留集/重复trial、judge校准和失败记录。
- 若只收集顺利示例时：模型更新后怎样避免只修已知题？
  - 期待证据：给证据不足和攻击样本的成功定义，以及费用分母和时间范围。
- 若已讲清核心流程但缺少可验证证据：请给出一个能检验“任务评估集”方案是否有效的失败样例和预期结果。
  - 期待证据：给证据不足和攻击样本的成功定义，以及费用分母和时间范围。 需要明确失败输入、预期终态和可观察断言，不能仅列工具名称。
- 若自报已经在项目中实现：在你负责的部分，“任务评估集”具体有什么输入、输出和可提供的证据？没有资料也可以说明限制。
  - 期待证据：给证据不足和攻击样本的成功定义，以及费用分母和时间范围。 还需区分本人实现与团队结果，给输入输出或脱敏材料；未提供材料只记自报，不声称核实。

最低合格：按任务类定义成功；拒答/越权分母独立；确定性与模型判定结合

- 未体现：未回答核心问题，或坚持“演示成功率就是线上成功率”且无法解释；只记录当前答案缺口。
- 基础理解：能解释典型、边界和失败样本，但尚未把情景处理流程说清。
- 可应用：能结合题目说明典型、边界和失败样本和可核验任务指标，给出可执行处理。
- 较完整：在可应用基础上覆盖隔离评估集及回归记录，给出验证方法并解释取舍。

### Q22-V1

原创假设：开发80题全见过，新增型号只在线上出现，禁止用客户秘密。

新版本在历史80题上满分，线上却把新型号答错；你怎样发现评测泄漏和分布漂移，构建不会只背题的更新流程？

期待证据：独立时间切分/新实体样本、评测泄漏与漂移检查。

## Q23 日志与追踪

能力 E07；前提：知道该模块的输入输出；没有生产经验可按题面假设回答，语言与框架不限定。

场景：假设用户反馈任务调用工具12次、费用翻倍；有model→search→rerank→answer链路，不能记录完整姓名、订单内容或API密钥。

问题：用户反馈Agent重复调用工具且费用翻倍，你会记录哪些信息定位问题，同时保护隐私？

- 若记录所有原始内容时：怎样定位重复又不记录完整客户资料？
  - 期待证据：给一条去敏trace并按父span解释重复发生在哪一层。
- 若已讲清核心流程但缺少可验证证据：请给出一个能检验“日志与追踪”方案是否有效的失败样例和预期结果。
  - 期待证据：给一条去敏trace并按父span解释重复发生在哪一层。 需要明确失败输入、预期终态和可观察断言，不能仅列工具名称。
- 若自报已经在项目中实现：在你负责的部分，“日志与追踪”具体有什么输入、输出和可提供的证据？没有资料也可以说明限制。
  - 期待证据：给一条去敏trace并按父span解释重复发生在哪一层。 还需区分本人实现与团队结果，给输入输出或脱敏材料；未提供材料只记自报，不声称核实。

最低合格：trace/span与版本关联；新调用/重试/重发区分；脱敏与最小留存

- 未体现：未回答核心问题，或坚持“把全部输入输出写日志最方便可靠”且无法解释；只记录当前答案缺口。
- 基础理解：能解释关联ID与阶段事件，但尚未把情景处理流程说清。
- 可应用：能结合题目说明关联ID与阶段事件和耗时、调用、token和终止原因，给出可执行处理。
- 较完整：在可应用基础上覆盖脱敏、访问与留存，给出验证方法并解释取舍。

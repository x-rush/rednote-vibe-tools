# 八项目玩法逻辑、必要资料与开发规划

## 1. 总体设计原则

八个项目都使用纯前端实现，但不能都做成“选择若干选项 → 生成一张结果卡”。每个项目需要拥有一个不同的核心动作：

| 项目 | 核心动作 | 用户获得的满足 |
|---|---|---|
| SBTI 山海兽格 | 在山海情境中做选择 | 被描述、认领一种兽格 |
| 物华录 | 看线索、辨文物、收图鉴 | 猜中、揭晓、收藏 |
| 大理寺字案录 | 审传言、查证据、下判词 | 发现误解、完成推理 |
| 汴京饮子铺 | 做经营决策、承担延迟后果 | 活过百日、赚钱、解锁结局 |
| 我希望被这样对待 | 选择、编辑、排序自己的需要 | 把难说出口的话整理清楚 |
| 出门检查官 | 配置场景、巡视空间、逐项勾选 | 降低遗漏和临出门焦虑 |
| 当时这样说就好了 | 分离事实与推测、重写表达 | 看清冲突、重新组织语言 |
| 地球 Online：冒险者公会大厅 | 登记冒险者状态、领取并完成现实任务 | 让平淡的一天发生一点变化 |

通用体验标准：

- 首屏 3 秒内说清价值，首次体验不要求注册、联网或阅读长教程。
- 30 秒内出现第一次有效反馈。
- 单轮在 1-5 分钟内完成；《汴京饮子铺》允许跨多次打开。
- 每个结果都有形成原因，不做纯随机“玄学结果”。
- 首发内容形成完整闭环；后续更新只扩展主题、题库、关卡或场景包。

## 2. SBTI｜山海兽格测试

### 2.1 用户钩子

“如果 MBTI 描述你在人群中的倾向，SBTI 会告诉你在山海世界中以怎样的方式生存。”

### 2.2 核心玩法

用户经历“入境、寻迹、异变、归来”四章，从首发 48 道原创题库中按规则抽取 24 道具体情境题做二选一。每个章节 6 道、每个维度 6 道主测题；选项为四组 SBTI 维度加权，最终形成四字母兽格并匹配一只已审核的异兽。

```text
进入山海 → 4题入境 → 4题寻迹 → 4题异变 → 4题归来
→ 计算连续倾向 → 平衡维度判定 → 异兽显形 → 兽格结果
```

### 2.3 单题逻辑

- 每题呈现一个明确冲突，而不是抽象自评。
- 两个选项都合理，分别体现不同偏好。
- 每题主要影响一个维度，最多轻微影响第二维度。
- 用户可以返回上一题；最终提交前可检查选择。

### 2.4 反馈与结果

- 答题中只做情境反馈，不即时揭示人格分数，避免用户操纵结果。
- 结果显示四维连续倾向、中文兽格名、主异兽、优势、代价、压力表现、关系需要和今日行动。
- 古籍原文与 SBTI 创意演绎分区展示。
- 接近中点的维度显示“较为平衡”，并提示一个相邻兽格。

### 2.5 重玩理由

- 查看相邻型。
- 让朋友测试并比较结果。
- 后续增加不同章节题库，但保留算法版本。

### 2.6 首发边界

16 固定题、16 种完整结果、16 只异兽、一个相邻型解释。不做好友匹配、关系配对、在线排行和 AI 对话。

### 2.7 必要资料

- 八个偏好端点定义。
- 16 种不含异兽的人格原型。
- 24-32 只候选异兽的原典资料和文化原型。
- 最终 16 型映射、证据置信度和来源。
- 48 道首发正式题；按 4 章节 × 4 维度建立覆盖矩阵，每个“章节 × 主维度”至少 3 道候选题。
- 单次抽取 24 道，不连续出现相同主维度，且控制左右选项对应端点的位置平衡。
- 16 张统一风格异兽图、章节背景、显形资源。

### 2.8 开发顺序

1. 冻结维度、类型和异兽映射。
2. 用纯文本完成问卷、计分和 16 个结果闭环。
3. 完成偏好明显、四维均衡、混合边界 3 次人工模拟，并用代码检查 16 型可达性。
4. 接入章节 UI 和本地历史。
5. 映射锁定后生成美术。
6. 加入显形动画、来源抽屉和性能降级。

## 3. 物华录：文物寻踪

### 3.1 用户钩子

“只看剪影和三条线索，你能认出这件古人真正用过的东西吗？”

### 3.2 核心玩法

每局出现 5 件文物。用户先看剪影或局部，可以直接作答，也可以逐步开启材质、用途和年代线索。答对后文物恢复原貌并收入图鉴。

```text
选择今日寻踪 → 文物剪影 → 直接猜/开线索 → 四选一
→ 揭晓与混淆解释 → 收入图鉴 → 下一件 → 五件结算
```

### 3.3 星级与反馈

- 不使用线索答对：3 星。
- 使用 1 条线索答对：2 星。
- 使用 2 条以上或首次答错后完成：1 星。
- 答错不阻止图鉴解锁，但必须解释“为什么容易认错”。
- 同一件文物可以通过提高星级形成二次挑战。

### 3.4 收集系统

- 图鉴显示已发现、星级、类别和资料来源。
- 未解锁项目只显示轮廓和一个模糊标签。
- 五件完成后生成收藏家偏好，例如日用器、宴饮器、礼仪器、出行器。
- 收藏家偏好来自答题和收藏行为，不是严肃人格测试。

### 3.5 重玩理由

- 每日种子局与自由练习。
- 补全 20 件图鉴。
- 将已解锁文物提升到 3 星。
- 后续按“古人的日常、宴席、出行、文房”扩展主题季。

### 3.6 首发边界

第一季 20 件文物、5 件一局、单一四选一题型。暂不做 3D、AR、在线排行、文物 AI 对话。

### 3.7 必要资料

- 20 件文物名称、时期、材质、用途、馆藏和来源。
- 每件文物 3 条由难到易的线索。
- 每件文物 3 个有逻辑的干扰项及混淆解释。
- 剪影、局部、揭晓图及版权/许可台账。
- 第一季分类体系和收藏家偏好规则。

### 3.8 开发顺序

1. 先完成 5 件文物黄金样例。
2. 实现题局、线索、星级、揭晓和图鉴闭环。
3. 真机验证图片加载与点击节奏。
4. 扩展到 20 件并完成来源审核。
5. 加入每日种子、图鉴筛选和收藏家结算。
6. 最后制作恢复原貌动画和参赛演示。

## 4. 大理寺字案录

### 4.1 用户钩子

“‘羊大为美’‘止戈为武’这些流传很广的汉字故事，真的经得起查吗？”

### 4.2 核心玩法

用户领取一宗文字疑案，先判断坊间传言，再依次查验字形、古义和历史语境。证据逐步出现，用户可修改判断，最终亲自落下判词。

```text
领取案卷 → 查看传言 → 初判 → 验字形 → 查古义
→ 审语境/争议 → 修改或坚持 → 选择判词 → 官方结案说明
```

### 4.3 断案机制

- 采用选项式 Galgame 交互：NPC 对话、追问方向、证据调查、真假判断和判词均为预设选项。
- 用户不输入自由文本，不需要系统分析自然语言；分支由本地 JSON、案件 flags 和有限状态机控制。
- 初判四档：可信、部分可信、证据不足、常见误解。
- 三项证据至少包含一种操作：找构件、年代排序、证词真假、语境配对。
- 结案前再次选择判词，系统记录用户是否根据证据更新判断。
- 评分重点不是猜中，而是证据使用和判断更新。

### 4.4 结果与收集

- 单案结果：判词、理由、争议范围、资料来源。
- 8 案完成后生成断案风格：形证派、语境派、审慎派、直觉派。
- “已结字案”支持重审和证据回看。

### 4.5 重玩理由

- 重审曾判断错误的案件。
- 收集 8 份判词。
- 后续增加“名字里的汉字、成语里的误会、网络热梗”新卷宗。

### 4.6 首发边界

8 个案件，每案 3 个调查步骤，全部采用预设选项。不做自由回答、自由查字、OCR、手写识别和 AI 实时解释。

### 4.7 必要资料

- 8 个传言及其权威字形、古义、历史语境和争议。
- 每案至少 1 个权威字书、学术出版物或可信机构来源。
- 古文字形 SVG 或可合法使用的字形资料。
- 每案 3 个互动证据和最终判词。
- 大理寺为虚构“字案”设定的历史边界说明。

### 4.8 开发顺序

1. 只做 1 宗完整黄金案件。
2. 验证“初判—证据—改判—结案”是否真正好玩。
3. 建立案件数据结构和证据组件。
4. 扩展到 4 案进行真机测试，再扩到 8 案。
5. 最后加入案卷 UI、朱批、盖印动画和断案风格结算。

## 5. 汴京饮子铺：开店一百天

### 5.1 用户钩子

“带着 300 文在汴京开一家饮子铺，你能撑到第 100 天吗？”

### 5.2 核心玩法

用户每天查看天气、节令和街市消息，决定备货或经营策略，处理一个主要事件，随后结算资金、口碑、体力和人情。早期选择可能在几十天后产生回响。

```text
晨间情报 → 备货/定价/今日策略 → 顾客或街市事件
→ 选择 → 当日结算 → 延迟后果/剧情旗标 → 自动存档 → 下一天
```

### 5.3 四项状态

- 资金：支付进货、租金和意外开支；低于倒闭线进入最后挽救事件。
- 口碑：影响客流、特殊客人和老字号结局。
- 体力：过低会触发失误、休业和健康风险，但不做医学内容。
- 人情：影响街坊帮助、连续故事和“没赚大钱但被记住”的结局。

### 5.4 每日决策

- 晨间只做一个轻经营选择，避免每天操作库存表过重。
- 主要事件提供 2-3 个有取舍的选项。
- 选项不能永远存在最优解，至少交换两项资源。
- 随机事件不能无预警直接结束游戏。

### 5.5 百日结构

- 1-10 天：学会营业，容错高。
- 11-30 天：建立熟客与第一条连续剧情。
- 31-60 天：租金、季节和竞争压力上升。
- 61-90 天：早期选择回归，经营路线分化。
- 91-100 天：结局条件逐步显现，仍保留挽回机会。

### 5.6 失败与结局

- 失败：资不抵债、积劳停业、门可罗雀、四面无援或特定剧情失败。
- 结局：勉强守店、街坊小铺、汴京名店、开出分号、钱多情薄、百日不涨价等。
- 分享卡显示存活天数、最终资产、最重要选择和结局。

### 5.7 重玩理由

- 不同随机种子和经营路线。
- 解锁不同连续人物故事。
- 收集 8 个以上结局。
- 挑战活过百日、最高资金或特定道德经营目标。

### 5.8 首发边界

单店型、100 天、四资源、80 个基础事件、5 条剧情链、8 个结局。不做地图、实时烹饪、多人排行和复杂供应链。

### 5.9 必要资料

- 宋代饮子、商业生活、钱币、节令和城市生活资料。
- 6-8 种商品及简化成本/售价体系。
- 80 个事件、5 条跨天故事、8 个结局。
- 3 张店铺背景、12-16 位顾客、商品、天气和结局美术。
- 历史事实与游戏平衡之间的明确标注。

### 5.10 开发顺序

1. 纯文本做 10 天闭环。
2. 建立无 UI 模拟器，检查资金和状态曲线。
3. 扩到 30 天并加入 2 条剧情链。
4. 验证事件冷却、延迟后果和存档。
5. 扩到 100 天、80 个事件和完整结局。
6. 每次数值改动跑至少 10,000 局模拟。
7. 数值稳定后再接入店铺、顾客和结局美术。

## 6. 我希望被这样对待｜关系说明书

### 6.1 用户钩子

“有些需要不是不想说，而是不知道怎么说。”

### 6.2 核心玩法

用户不是被测出一个人格，而是通过选择得到一份可编辑初稿，再主动决定哪些需要愿意展示、如何措辞以及自己愿意做出什么承诺。

```text
选择关系版本 → 12-16 个偏好选择 → 生成初稿
→ 编辑/隐藏/排序 → 补充自己的承诺 → 简版/完整版预览 → 本地保存
```

### 6.3 七个章节

1. 我累的时候。
2. 我难过的时候。
3. 我们发生矛盾时。
4. 我如何感受到被重视。
5. 哪些安慰对我无效。
6. 我的边界和提醒方式。
7. 我愿意怎样对待你。

### 6.4 核心互动

- 每题允许“都不像我”和“我想自己写”。
- 结果不是只读卡片；编辑、隐藏和排序是核心玩法。
- 敏感内容默认不进入适合截图的简版。
- 用户完成前必须检查“要求”和“承诺”是否失衡。

### 6.5 重复使用理由

- 随关系和生活阶段修改。
- 后续增加好友、室友、合作伙伴版本。
- 本地保存不同关系的独立说明书。

### 6.6 首发边界

只做一个关系版本、一份草稿、简版和完整版。不做双人匹配、心理标签、自动发送和云同步。

### 6.7 必要资料

- 12-16 道偏好题及对应输出语句。
- 情绪支持、冲突、边界、提醒方式等中性表达库。
- 7 章至少各 12 条候选句。
- 敏感句标记和简版过滤规则。
- “我愿意怎么做”的承诺句库。

### 6.8 开发顺序

1. 先用 6 道题生成一份可编辑说明书。
2. 验证编辑、隐藏、排序和本地保存。
3. 扩展到完整 7 章和 12-16 题。
4. 增加简版/完整版和敏感信息检查。
5. 最后打磨信件式 UI 和截图构图。

## 7. 出门检查官

### 7.1 用户钩子

“不是再给你一张万能清单，而是在关门前按遗漏代价和房间路线检查一次。”

### 7.2 核心玩法

用户选择出行场景和条件，规则引擎生成清单。用户可以在“优先级模式”准备物品，再进入“空间巡视模式”按家中路线完成最后检查。

```text
选择场景 → 选择时长/交通/过夜/天气/同行条件
→ 生成清单 → 自定义增删 → 优先级准备
→ 空间巡视 → 最后一分钟确认 → 保存/完成
```

### 7.3 三种视图

- 优先级：绝对不能忘、忘了很麻烦、现场可以买。
- 类别：证件、电子、衣物、健康等。
- 空间：床头、插座、卫生间、书桌、冰箱、玄关。

### 7.4 规则逻辑

- 场景提供基础项。
- 时长、交通、过夜、天气和同行条件增加或删除项目。
- 关键项具有最高优先级，不能因缺少非必要答案而消失。
- 用户可添加私人项目，但不上传。
- 天气和位置由用户选择，不调用定位或实时接口。

### 7.5 重复使用理由

- 保存最近 3 份清单并继续勾选。
- 复制已有清单作为新行程。
- 后续增加面试、婚礼、搬家、带娃和宠物等场景包。

### 7.6 首发边界

8 个场景、三种视图、最近 3 份清单。本地运行，不做自动天气、地图、账号和模板市场。

### 7.7 必要资料

- 8 个场景基础清单。
- 项目标签、优先级、空间位置和条件规则。
- 典型组合测试样例。
- 交通和场所相关提醒的保守文案及来源。

### 7.8 开发顺序

1. 完成“一日短途”和“三日出差”两个黄金场景。
2. 实现规则引擎和三种视图。
3. 建立组合快照测试，防止关键项丢失。
4. 扩展到 8 场景和自定义项。
5. 加入最近清单、复制、清空和巡视模式。

## 8. 当时这样说就好了

### 8.1 用户钩子

“吵完之后才发现，我真正想说的其实不是那句话。”

### 8.2 核心玩法

它不是自动生成高情商话术，而是让用户将同一次对话拆成事实、感受、解释、需要和请求。每一步都要求用户主动辨别，最终得到可编辑表达。

```text
选择无痕/本地模式 → 当时发生了什么 → 当时感受到什么
→ 脑中出现了什么解释 → 标记事实/推测 → 真正需要什么
→ 希望对方做什么 → 如果再说一次 → 编辑最终表达
```

### 8.3 核心辨别机制

- “昨晚发消息后到中午没收到回复”可以作为事实。
- “他根本不在乎我”属于解释或推测。
- 用户把句子拖入“可观察事实”或“我的理解”，系统再给示例提示。
- 系统不判定用户的推测为真或假，只提醒证据边界。

### 8.4 输出规则

最终表达由用户内容按模板重组：

```text
当……发生时，
我感到……，
因为我在意/需要……，
我想请求……。
```

输出必须可编辑、可删除；不承诺换种说法就能解决问题，也不把冲突责任归给用户。

### 8.5 重复使用理由

- 不同对话分别复盘。
- 后续增加朋友误会、工作沟通和家庭沟通引导。
- 本地回看自己常混淆的事实与推测，但不做心理诊断趋势。

### 8.6 首发边界

5 步引导、情绪词和需要词、可编辑结果、无痕模式和最近 3 次本地记录。不上传聊天截图，不分析对方，不做关系评分。

### 8.7 必要资料

- 50-80 个情绪词和 30-50 个需要词。
- 事实/推测对照样例。
- 20-30 个可编辑表达模板。
- 隐私、安全和紧急伤害提示文案。
- 敏感内容本地存储和清空规则。

### 8.8 开发顺序

1. 用一个示例对话完成 5 步闭环。
2. 实现无痕模式和本地模式。
3. 验证事实/推测分类与模板重组。
4. 扩充情绪、需要和请求内容库。
5. 进行安全文案评审和长文本移动端测试。

## 9. 地球 Online：冒险者公会大厅

### 9.1 用户钩子

“主线不用着急，先来领一个小任务。”

### 9.2 核心玩法

用户以“地球 Online 冒险者”的身份登记当下条件，系统先进行安全硬过滤，再根据目标感受、偏好和最近历史加权，从公会任务板匹配一个具体任务。用户可以接取、完成、收藏、标记不适合或有限次数更换。`Online` 仅是 RPG 世界观，任务在本地生成，不依赖网络。

```text
选择时间/精力/预算/室内外/社交意愿/目标感受
→ 安全硬过滤 → 偏好加权 → 支线揭晓
→ 查看2-4个步骤 → 完成/收藏/不适合/换一个
→ 本地记录 → 降权最近任务
```

### 9.3 推荐逻辑

- 硬过滤：时间、预算、环境、昼夜、天气、社交和安全。
- 软加权：目标感受匹配、收藏过的类别、最近没出现的主题。
- 降权：点过“不适合”、最近完成、同类连续出现。
- 无结果时只放宽软条件，永不放宽安全条件。
- 天气、位置由用户输入；不依赖网络。

### 9.4 任务质量

差的任务：“出去走走。”

好的任务：“在 15 分钟内找到三种今天才注意到的影子：规则形状、会移动的、叫不出来源的。”

任务必须具体、低门槛、不骚扰陌生人、不鼓励危险、违法、冲动消费、饮酒或博彩。

### 9.5 反馈与重玩

- 完成后只做轻量确认，不建立强迫性打卡。
- 支线历史形成“生活切片”，可本地收藏。
- 后续增加五分钟、雨天、下班后、城市观察和微型创作任务包。

### 9.6 首发边界

100 条人工审核任务、条件过滤、完成/收藏/不适合、历史和冷却。不做地图、定位、自动天气、陌生人匹配、公共任务上传、用户图片选择或图片本地存储。

### 9.7 必要资料

- 100 条结构化任务及 2-4 个步骤。
- 时间、预算、精力、环境、社交、目标感受和安全标签。
- 夜间、雨天、低精力、零预算等组合测试集。
- 禁止任务类型和安全审核清单。

### 9.8 开发顺序

1. 先写 20 条黄金任务，覆盖关键条件。
2. 实现过滤、加权、冷却和降级。
3. 建立条件矩阵自动测试。
4. 扩展到 100 条审核任务。
5. 加入历史、收藏、不适合和轻量完成反馈。

冒险日志只保存体积可控的结构化数据，例如任务 ID、完成时间、收藏状态和有限长度的文字备注；不保存用户图片。少量记录可用 `localStorage`，记录增多或需要索引查询时可使用 `IndexedDB`。

## 11. 跨项目开发顺序

每个项目遵循同一闸门：

```text
玩法冻结
→ 5-20条黄金内容
→ 无美术可玩原型
→ 数据结构与自动测试
→ UI信息架构
→ 内容扩写与人工审核
→ 风格基准图
→ 批量美术/音频
→ 集成与性能优化
→ 手机尺寸测试
→ 小红书真机测试
→ 构建上传包与参赛内容
```

### 并行开始条件

只有当“玩法冻结、数据字段冻结、黄金样例通过”后，才并行启动：

- UI/交互：页面、状态、设计令牌和动效。
- 内容：批量扩写、来源、审核和版本。
- 美术：风格基准、批量资源、许可和压缩。
- 代码：引擎、存储、数据加载、测试和降级。

### 单项目停止条件

出现下列任一情况时，不进入下一项目的批量阶段：

- 核心循环只有连续点击“下一步”。
- 黄金样例尚未通过人工审核。
- 关键数据字段仍频繁变化。
- 无法在手机端完成完整一轮。
- 内容依赖未经核验的历史或心理学说法。
- 首发闭环需要后端、定位、实时 API 或不稳定浏览器能力。

## 12. 推荐的规划讨论顺序

不要把一个项目研究到底再发现其他项目玩法高度重复。建议先完成八个项目的玩法冻结，再逐个进入资料细化：

1. 确认本文列出的八个核心循环是否符合预期。
2. 为每个项目确定首发内容数量和单局时长。
3. 为每个项目选定唯一的“30秒高光时刻”。
4. 确认重玩/复用理由和明确不做项。
5. 再从 SBTI 开始，逐个完成必要资料规格与黄金样例。

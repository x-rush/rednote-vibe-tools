# 弹珠神殿（34 号）

复刻自 eazo.ai 的 `Billiard Temple`，改造成纯前端静态小红书小工具。

- **一句话**：按住玉球向后拖，松手击球；撞到的宝石会变成新的球，连锁越滚越大。
- **平台简介**：一颗玉球，八重金殿
- **来源**：[eazo.ai Billiard Temple](https://eazo.ai/apps/billiard-temple-physics-puzzle-ogvlurbo)
- **批次方案**：见 `projects/31-shuttlecock-kick/PLAN.md`（31–35 号批量复刻方案）

## 玩法

1. 一颗翠玉弹珠停在殿堂底部。**按住玉球向后拖动瞄准（弹弓），松手击球**（拖得越远越快，蓄力时球会亮起光晕；快速点按与拖拽不足都绝不发射，拖动中绝不发射）。
2. **宝石变球连锁（核心爽点，原版同款）**：被任何球撞到的宝石会变身成一颗新的连锁球继续滚动（继承撞击速度 + 确定性扇出偏转，同杆上限 12 颗）——一杆之内球越滚越多，滚雪球式收完整殿。连锁球之间弹性碰撞；连锁球不与玉球互撞（原版同款：否则玉球会被自己的连锁球挡路撞停）。连锁越高，音阶越高（五声音阶递进），连锁到 3/6 颗触发慢镜 + 屏震 + 横幅。
3. 瞄准线是一条带箭头的能量线，第一段实线、第二次反弹的虚线——但只到第一次为止，后面要自己判断。
4. **每殿 4 杆，宝石收齐即进下一殿，杆数用完重打本殿（宝石重置）**。宝石数按原版经济：第 n 殿 = 5 + min(5, n)（第 1 殿 6 颗，第 5 殿起 10 颗）。**一杆清空**仍有全屏光爆 + 慢镜，宝石图鉴同步点亮。
5. 统计：单杆连锁数（runGems）、整局最高连锁（bestRun，结算面板与技巧卡展示）。八殿走完生成 720×960 技巧卡与八颗宝石图鉴。

### 弹弓输入回归（真机 bug 修复）

真机试玩出现「还没松手就发射了」。根因有三，全部修复并有回归测试：

1. **`#field` 的 `touch-action: manipulation` 允许浏览器接管拖动手势**：真机拖动瞄准时浏览器判定为平移就发 `pointercancel`，旧代码把它当 `pointerup` 处理 → 拖动中途发射。现在画布 `touch-action: none`，且 `pointercancel` 单独处理为「中止瞄准，绝不发射」。
2. **无 pointerId 归属**：第二根手指抬起也会发射。现在输入状态机只认「按下的那根手指」。
3. **无最短按住时长**：快速点按远处也会立即发射。现在按住 < 80ms 或拖拽 < 14px 一律不发射。

输入判定收敛在 `game.createAimInput`（纯逻辑状态机，Node 单测直接驱动事件序列：按下→拖动 500ms→松手断言只在松手时发射一次；快速点按、pointercancel、多指、重复 up 全部有断言）。

## 手感设计

- **反弹必须真的吃角度与摩擦**。球是匀减速运动的，撞墙按恢复系数 0.88 反弹、切向有损失、停下来就停在原地。力小就飞不到，角度差一度路线就完全不同——所以每一殿都是「算角度」的关卡，不是「连线消除」。
- **机关是固定石柱 + 沿轴往复的闸条**。放弃旋转横杆：横杆的扫掠区是整块圆盘，会把整条路堵死；沿轴往复的闸条既能挡路，又留得出可以穿过去的缝。
- **闸条按殿堂绝对时间匀速来回**：每条闸条写明 `period`（周期，秒）、`phase`（相位 0~1）、`duty`（0.5 = 匀速），**同一殿里所有闸条共用同一个 period**（本项目统一 4 秒）。于是「石条每 4 秒来回一次」是可数的节奏，玩家瞄一眼滑轨就能预判它下一刻在哪。
- **可解性仍是「先有解、后摆宝」**：扫角度×力度挑出余量充足的「标称杆」，一半宝石（parGems）摆在轨迹上（构造保证的直接收获），其余在连锁走廊散布、部分放远区——连锁球够得着走廊、够不着远区，一殿至少要两条进攻线。宝石避开扫掠区边缘口袋、贴墙带与四角夹角（这些位置的宝石进攻角度太窄）。任意起手时刻「标称杆直收 parGems 且不蹭机关」是构造保证，连锁的扇出偏转用宝石坐标哈希保持确定性。

### 这里返工过两次，值得写下来

早期版本的平衡回归用「轨迹有没有压到石条扫掠区」来保证**相位无关**（石条换个相位，这一杆照样成立）。判据用的是严格不等式，结果出过一次假绿：

> 第六殿的标称轨迹**正好擦过**扫掠区的角点——球心 x 恰好等于扫掠区左边界（29.0 vs 29），被判成「没压到」。实际上这时球与石条的距离正好等于球半径，石条换个相位往前挪 4px，球就蹭上去，那一杆从 6/6 颗宝石掉到 1/6 颗。

修正分三步：

1. **物理层把「撞墙」和「蹭机关」分开计数**（`shot.wallBounces` / `shot.propHits`）。原来 `bounces` 把两者混在一起，导致生成器在找「4 次反弹」的杆时，挑中了一堆蹭机关的路径——「4 次反弹」实际是 3 次撞墙 + 1 次蹭机关。
2. **生成器改为算余量而不是判「有没有压到」**：轨迹到障碍扫掠区的最短距离必须 ≥ 6px。这一条直接把第六殿那杆相切路径否掉了。
3. **回归从「代理指标」换成「正面校验」**：不再用扫掠区这种间接判据，而是把起手时间在 0–8 秒之间密集扫一遍（覆盖闸条的两个完整运动周期），要求**每一次起手，标称杆都照样一杆清空且完全不蹭机关**。这条才是玩家真正能感知的性质。

二期返工又补了两条同类断言：

4. **机关必须是周期性的、匀速的**：同一殿的闸条共用同一个 `period`，整周期内每等分时间步的位移大小相同——玩家能预判，才谈得上「可读」。
5. **配额必须是收紧的**：随手玩家用杆必须落在「配额 - 2 ~ 配额」之间，否则配额形同虚设（第七/八殿明确断言 6 杆 / 8 杆）。

## 工程约束

- 纯前端静态：经典脚本加载链，禁 `type="module"` / `import` / `eval` / 内联脚本 / 行内事件。
- Chrome 61 / Android 8.1 WebView 61 基线：ES2017，CSS 不使用 flex `gap`、`clamp()`、`aspect-ratio`、逻辑属性、`:has()`、`inset`、`dvh`；Canvas `roundRect` 手写路径。
- 无后端、无运行时 CDN、无必需外部 API、无音频文件：音效全部由 Web Audio 实时合成。
- 业务内容集中在 `src/content/content.json`（含 `brand` / `xiaohongshuDraft` / 8 关配置 / 文案 / 8 套配色 / 8 种宝石）。
- 只在 localStorage 保存结构化状态（最高分、宝石图鉴、静音偏好），不保存任何用户媒体。
- 宿主按钮避让：顶部左右各留 `--host-side: 76px`，标题与 HUD 在 `--host-top: 56px` 之下；横屏改成三栏，左栏让开左上返回键、右栏让开右上操作键。
- 上架素材不复用任何历史条目素材，logo 为本项目原创。

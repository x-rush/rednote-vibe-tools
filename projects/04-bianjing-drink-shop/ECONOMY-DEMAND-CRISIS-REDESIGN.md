# 《汴京饮子铺：开店一百天》经营闭环与周转危机重构规格

状态：已完成逐节确认，待用户审阅书面规格
日期：2026-08-27
范围：仅 `projects/04-bianjing-drink-shop`

## 1. 背景与目标

现版本存在四个相互放大的问题：

1. 账簿按饮子汇总收入，却容易让玩家误以为每日固定只有三笔生意；营业演出还可能漏掉第五种饮子。
2. 备货页只从现钱中扣除原料成本，没有预留房钱和开门杂费，界面显示“资金足够”时仍可能在结算后直接负债。
3. 顾客需求只在已上架饮子之间分配，未模拟“想喝的没有准备”“售罄后转买或离店”。天气又在备货后才揭晓，玩家缺少可行动的晨间情报。
4. 休业仍扣房钱，却屏蔽普通事件和待触发后续事件；低资金没有确定性转机，资金跌破零后直接失败，形成没有决策空间的死亡螺旋。

本次重构要形成如下核心体验：

> 读懂晨间线索 → 选择菜单并承担风险 → 看见具体顾客的反应 → 得到账面与剧情反馈 → 今天的选择在以后回来。

定位为“轻策略经营＋真实失败”：当下方向清楚、结果保留有限不确定性；失败必须可解释，翻身必须来自玩家选择和既往关系，不能依赖随机送钱。

## 2. 已确认的设计原则

- 每局必有一次基础救急机会；口碑、人情和既往事件可解锁条件更好的方案。
- 备货量只限制最多能卖多少，不会凭空创造需求，也不保证全部售出。
- 顾客先形成原始偏好，再判断菜单是否满足、是否接受替代、是否因价格或缺货离开。
- 晨间提供可行动但不精确的情报；不展示唯一最优答案。
- 经营主界面不再显示 M/H/R 等缩写，统一使用“现钱、体力、口碑、人情”及原因说明。
- 重大事件不必每日发生；日常经营每天都有简短反馈，人物连锁和约定后续按逻辑优先发生。
- 所有运行时业务内容和可调参数只进入 `src/content/content.json`；TypeScript 只实现通用规则。
- 不新增后端、运行时 CDN、外部 API、Service Worker 或设备能力，不新增依赖。

## 3. 每日状态与数据流

每日按以下固定顺序推进：

1. `morning-forecast`：使用存档 RNG 生成当天唯一的天气、客群偏好、市场线索与隐藏波动，并立即持久化。
2. `preparation`：玩家根据晨间情报选择全日、半日或休业，设置 3–5 种饮子、备货量和售价。
3. `opening-review`：以与最终结算相同的成本函数展示完整支出和预测区间。
4. `opening/business-event`：若有开门或营业中事件，按优先级处理；事件造成的需求变化写入当天上下文。
5. `demand`：生成原始偏好，依次处理价格、菜单匹配、备货上限、替代购买和流失。
6. `settlement`：统一结算销售、剩货折返、固定成本、到期义务和事件效果。
7. `financial-health`：结算后判断正常、预警、周转危机或正式歇业。
8. `closing/follow-up`：显示当日主因、未来线索并保存下一日状态。

天气和市场线索一旦生成，刷新、返回首页、继续游戏或恢复存档都不得重新抽取。已开门的当天不得因版本迁移或恢复操作重算需求与账目。

## 4. 晨间情报

晨间先揭晓当天真实天气，并展示三类信息：

- 天气及其经营影响，例如“暑热：清凉、酸爽偏好上升”。
- 一条市井客群线索，例如“码头今日卸货，脚夫增多”。
- 一条基于昨日结算的经营提醒，例如“青梅饮昨日午前售罄”。

阿元以大尺寸轻 Galgame 立绘说明情报。情报只给方向，不给准确客人数；隐藏波动仍会让最终需求在预测区间内变化。

## 5. 原始需求模型

### 5.1 顾客先有偏好，菜单后匹配

系统先按天气、季节、当日客群、口碑和事件修正，生成若干聚合需求组。需求组使用内容中的偏好标签，例如：

- 清凉、酸爽
- 甘甜、温润
- 草木、清淡
- 温热、辛香
- 新奇、招牌

每组包含人数、主要偏好标签、可接受替代标签和最高接受价格比例。只有当前存档已解锁饮子能够成为实际购买对象；未解锁饮子不得制造玩家无法满足的惩罚性需求。

### 5.2 购买顺序

每个需求组按以下顺序处理：

1. 从已上架、仍有备货且命中主要偏好的饮子中选择首选。
2. 首选不存在或售罄时，从命中可接受替代标签、价格不高于该组上限的饮子中尝试转买。
3. 转买概率由内容参数决定，并受口碑和价格差影响；不接受替代者离店。
4. 菜单有目标饮子但备货为零，按缺货处理。
5. 菜单无匹配饮子，按菜单不匹配处理。
6. 有匹配饮子但超过价格上限，按高价流失处理。

数量必须守恒：

`潜在购买人数 = 正常售出 + 转买售出 + 缺货流失 + 菜单不匹配流失 + 高价流失 + 服务能力流失`

同一位顾客最多购买一盏，不得在首选和替代品上重复计数。

### 5.3 备货和销量

对每款饮子：

`实际销量 = min(分配到该饮子的有效需求, 备货量)`

备货量不会参与偏好评分，只决定销售上限。备得多不等于卖得多；备得少会形成售罄与缺货。售罄后的顾客只能按替代规则转买一次，不能无限重分配。

### 5.4 需求预测

备货页根据当前已知天气、客群、模式、菜单和售价展示模糊区间：

- 走俏：预计 5–7 盏
- 平稳：预计 3–5 盏
- 偏淡：预计 1–3 盏

具体区间由统一预测函数计算，而非在 JSX 中硬编码。目标是实际需求约 75%–85% 的日子落在预测区间内；其余偏差必须来自已保存的隐藏波动或当天事件，不能来自刷新重抽。

## 6. 剩货规则

备货代表当天已经分装或预处理的可售份数。未售份数不跨日保存，避免引入繁重库存管理；但未启封原料、可回收膏底或干料可以折价收回。

每款饮子在内容中声明 `shelfClass`，统一映射折返比例：

| 保存类型 | 折返比例 | 说明 |
| --- | ---: | --- |
| `fresh` | 10% | 鲜果、鲜叶等当日损耗高 |
| `brewed` | 25% | 已煎煮饮子只能回收少量余料价值 |
| `dry` | 35% | 未用完的干料较容易留存或退回 |
| `concentrate` | 45% | 膏底、蜜底可回收比例最高 |

初始饮子分类如下：

- 青梅饮、薄荷饮：`fresh`
- 紫苏熟水、莲房饮：`brewed`
- 香豆饮、桂香饮、枣香汤：`dry`
- 姜蜜水、荔枝膏水：`concentrate`
- 百日招牌饮：`brewed`

剩货折返继续按整文钱向下取整，但备货页必须提前显示该饮子的折返率；结算明确显示原始成本、剩货数量、折返金额和实际损失。

## 7. 统一成本与经营模式

所有页面与最终结算共用同一个成本估算入口：

`开门后现金 = 当前现钱 − 备货成本 − 房钱 − 营业杂费`

现有基础成本保持为：

- 全日经营：房钱 4 文＋杂费 2 文。
- 半日经营：房钱 4 文＋杂费 1 文。
- 休业：房钱 4 文，无营业杂费，恢复 18 点体力。

重平衡后若数值调整，只改内容配置，不允许 UI、估算和结算各存一份常量。

备货页同时显示：现钱、备货成本、房钱、杂费、开门后现金、预计结算区间、售罄风险和剩货风险。

- 悲观区间可能跌破零：允许继续，但必须二次确认。
- 计划本身必然无法支付开门成本：不得显示“资金足够”，必须引导调整或处理周转危机。
- 休业仍扣房钱，但不得播放营业客流、生成营业收入或营业事件。
- 休业可以触发逻辑上合理的来信、街坊探望、到期还账、人物后续和救急剧情。

## 8. 财务状态、救急契约与失败

### 8.1 财务状态

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| 正常 | 现钱 ≥ 16 | 正常经营 |
| 周转预警 | 0 ≤ 现钱 < 16 | 明确提示最低三款备货与半日成本压力；可调整或提前使用救急 |
| 周转危机 | 现钱 < 0 且本局救急未使用 | 暂停失败判定，进入确定性救急剧情 |
| 三日周转期 | 已选择救急且宽限未结束 | 显示剩余天数、现钱、欠账和契约义务 |
| 正式歇业 | 救急后再次满足失败条件 | 进入“灶火暂歇”结局 |

16 文来自当前最便宜三款各备一份加半日固定成本，是预警线而非直接失败线。

### 8.2 触发顺序

先结算销售、固定成本、到期义务和当天事件，再检查最终现钱。第一次跌破零时不得直接显示结局；先显示亏损账目，再由阿元引入独立危机场景。

为保证基础救急确实有意义，内容校验限制普通可选事件的单次即时现钱损失不低于 −20 文；高于此风险的剧情必须拆成已预告的分期义务或连锁节点。

### 8.3 契约选项

1. **典当备用铜壶**：始终可选。立即获得 28 文；未来 7 个营业日体力消耗额外增加 2 点。表现为器具不足、制作更累。
2. **街坊联保赊账**：人情达到 35，或具有对应帮助旗标时开放。立即获得 22 文；第四日和第七日各归还 11 文。无利息，但必须出现还账后续剧情。
3. **熟客三日预订**：口碑达到 35 时开放。先收 16 文订金；三日内完成 12 盏指定偏好饮子，再收 16 文并增加口碑；未完成则没有尾款并损失口碑。

所有选项必须显示即时所得、持续时间、确定义务和未知后果提示。基础方案每局永远存在，较好方案由此前经营积累解锁。

### 8.4 三日周转期

- 从选择契约后的下一个自然日开始计三日；休业同样消耗期限，刷新、关闭和继续游戏不得重置。
- 宽限期内现钱可暂时为负，但不得低于 −20 文；跌破 −20 文立即歇业。
- 第三日结算后现钱达到 0 或以上，视为渡过危机。
- 第三日结算后仍低于 0，正式歇业。
- 渡过危机后救急机会视为已消耗；此后任何结算再次跌破 0，直接歇业。
- 已排定的赊账还款在渡过危机后仍须执行，不能因宽限结束消失。

## 9. 事件与经营联动

### 9.1 事件职责

- 晨间风声：备货前改变客群、原料价格或需求方向。
- 柜前小事：营业中围绕缺货、替代、排队、找钱、赊账和服务能力展开。
- 人物连锁：记录对具体人物的态度，在数日后产生回访、合作、误解或帮助。
- 周转危机：只处理确定性救急，不进入普通随机池。

每个事件必须具备完整因果链：

`发生原因 → NPC 真实诉求 → 玩家选择 → 当下结果 → 后续悬念`

### 9.2 数值语义

- 现钱变化必须对应具体收支。
- 口碑变化必须有人看见、传播或形成公共评价。
- 人情变化只来自具体人物关系。
- 体力变化必须对应劳动、休息或身体负担。

内容审计必须阻止选择文案、结果文案、影响提示与实际效果方向互相矛盾。归还失物、补回多收铜钱等守信行为不能无因损伤口碑。

### 9.3 频率与优先级

优先级固定为：

1. 周转危机或到期契约节点。
2. 已到期人物连锁节点。
3. 已约定后续事件。
4. 当日普通重大事件。
5. 无重大事件，仅播放顾客经营反馈。

普通重大事件概率调整为全日 50%、半日 40%；休业不抽取营业事件。非营业型后续事件可声明允许在休业日发生。人物连锁与后续一旦到期，不能被休业状态无声吞掉。

低资金转机只由救急系统保障。普通事件可以产生收入，但不得承担“随机抽中才能继续游戏”的职责。

## 10. 每日界面体验

### 10.1 晨间

保留阿元的大尺寸轻 Galgame 立绘与对话框。首屏只突出天气、街面客群和昨日提醒，按钮进入备货。

### 10.2 备货

每款卡片突出今日倾向、预计需求区间、备货数量、售价、保存类型、售罄风险和剩货风险。提供“沿用昨日方案”和“采用阿元建议”；建议只保证合理，不保证最优。

底部资金摘要处于正常文档流，不使用遮挡内容的悬浮定位。主按钮前完整显示成本与预计区间。

### 10.3 开门确认

列出菜单、数量、总备货成本、固定支出、预计资金区间和主要风险。风险确认不能用颜色作为唯一提示，必须同时有文字和可访问状态。

### 10.4 营业

营业固定分早市、近午、午后、落日前四个时段，与菜单数量无关。每个时段展示可理解的市井反馈，例如正常购买、售罄转买、缺货离店或高价离店。不能再把按饮子汇总的账目表现成三位顾客或三笔订单。

### 10.5 结算

首屏回答：今天赚亏多少、主要原因是什么、明天要注意什么。详细账簿折叠展示每款饮子的原始需求、备货、正常售出、转买售出、各类流失、剩货折返和固定成本。

阿元以大尺寸结算立绘总结主因；详细数字不得盖住人物面部或场景文字。

### 10.6 周转危机

使用独立剧情页面、大尺寸人物立绘和契约卡片，不使用普通弹窗。三日周转状态持续显示，但不能遮挡晨间、备货或结算主体。

### 10.7 响应式和实机导航

所有游戏页面为宿主顶部导航栏与安全区预留空间。重点验证 375、390、430 CSS px 和桌面宽度：无横向溢出、文字居中关系正确、主次按钮对比清晰、主要操作始终可见。

## 11. 技术模块

- `forecast`：生成并冻结每日天气、市场线索、需求组和隐藏波动。
- `demand`：处理原始需求、首选匹配、价格拒绝、售罄、一次替代和流失守恒。
- `economy`：统一处理估算与最终账目，输出可解释的结构化结算。
- `financial-health` / `crisis`：管理预警、契约资格、三日计时、义务与失败。
- `events`：管理事件资格、场景类型、优先级、连锁和后续。
- `view-model`：把结构化结果转换为玩家文案；React 组件不得重复业务计算。

这些模块通过类型化数据通信。每个模块保持纯函数优先，并显式接收 RNG 状态或被冻结的日上下文。

## 12. 存档 V4 与恢复

存档升级为 V4，新增但不限于：

- 当日冻结晨间情报和 RNG 状态。
- 结构化原始需求与营业结算结果。
- 财务状态、救急是否使用、契约类型、剩余宽限日和到期义务。
- 昨日方案和昨日主因摘要。

V3 自动迁移规则：

- 尚未开门：使用当前存档 RNG 生成一次晨间情报并保存。
- 已开门：保留原 `pendingOpening`，不重算天气、需求或账目。
- 根据当前现钱初始化正常或预警；迁移本身不得消耗救急机会。
- 已经处于旧版负数但尚未展示结局的存档进入周转危机。
- 已有正式结局保持原结局，不反向复活。
- 迁移失败时继续使用上一日可恢复存档，并向玩家说明恢复原因。

## 13. 错误与边界情况

- 菜单 3–5 种限制仅适用于全日和半日；休业菜单必须为空。
- 备货可设为零，但零备货明确标记为缺货风险，不能产生收入。
- 没有任何符合需求的菜单时，需求全部进入可解释的流失类别。
- 替代品售罄后不得再次递归寻找替代，避免重复或循环分配。
- 事件若改变当天需求，预测页标记为“开门后变化”，结算说明偏差原因。
- 到期契约、连锁节点和普通事件同日竞争时按既定优先级执行；低优先级内容顺延而非丢失。
- 休业期间宽限日是否推进按“自然日”计算，因此会推进；预订履约只按营业日计算并明确显示。
- 事件选择、结算或存档过程中失败时保留当日开始前快照，禁止重复结算同一日。

## 14. 测试与验收

### 14.1 规则测试

- 潜在需求数量守恒，销量不超过备货。
- 未上架、备货为零或售罄的饮子不得凭空产生收入。
- 同一顾客最多完成一次正常或替代购买。
- 估算和最终结算对固定成本、备货成本使用同一函数。
- 各保存类型折返金额与向下取整一致。
- 相同种子和决策得到相同天气、需求、事件与账目。
- 休业不产生营业收入或营业事件，但允许已声明的非营业后续。

### 14.2 救急和存档测试

- 基础典当始终可选，条件方案仅在满足门槛时出现。
- 救急每局最多使用一次。
- 三日计时、−20 文下限、第三日恢复判定和再次负债失败均正确。
- 赊账分期和预订目标跨刷新、迁移和继续游戏保持一致。
- V3 的晨间、已开门、负债、结局和恢复快照分别覆盖迁移测试。

### 14.3 内容语义测试

- ID 唯一、引用存在、条件可达、连锁变体不重叠。
- 选择文案、结果文案、影响提示和数值方向一致。
- 口碑、人情、体力和现钱变化满足各自语义约束。
- 任一普通可选事件的即时现钱损失不得低于 −20 文。

### 14.4 平衡目标

固定种子批量模拟目标：

- 能读懂情报的稳健策略百日存活率 75%–90%。
- 普通基础策略百日存活率 55%–75%。
- 长期高价或严重过量备货策略百日存活率低于 40%。
- 普通路线触发一次周转危机的比例约 20%–35%。
- 不存在只能休业扣钱、无法采取有效行动的软锁路线。

### 14.5 完整验证

在项目目录执行：

```bash
pnpm lint && pnpm test && pnpm build
```

使用真实浏览器验证 375、390、430 CSS px 和桌面宽度；检查顶部导航安全区、无横向溢出、按钮对比、焦点顺序、恢复流程和控制台零错误。

## 15. 非目标

- 不制作逐个顾客的复杂 AI；需求组保持聚合且可测试。
- 不加入跨日成品库存、仓库扩建、贷款市场或复杂利息系统。
- 不让阿元建议自动求解最优策略。
- 不依赖随机事件兜底破产。
- 不重写与本次经营闭环无关的结局、美术或页面。

## 16. 完成定义

只有同时满足以下条件才算完成：

1. 玩家在备货前知道可行动的天气和客群方向。
2. 玩家能解释每一类销量、流失、剩货和收支。
3. 资金不足时至少存在一次确定、可选择且有代价的翻身机会。
4. 失败前有预警、完整账目和明确原因，不发生无提示死局。
5. 剧情选择与经营规则互相产生可见后果，且不存在因果倒置。
6. 100 日重复操作通过沿用方案、合理建议和分层账目得到控制。
7. 全部自动检查和目标尺寸实机验证通过。

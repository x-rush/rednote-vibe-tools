# E02 解法与教学示例

## Q04 工具契约与参数

假设refund(order_id, amount)允许整数分，范围1..50000；输入可能缺order_id、amount=-1或订单属于他人。工具不接受模型提供的授权证明。

### 最低合格

工具用途单位和前置条件；schema后仍业务授权；call_id回填

### 完整参考解法

我会先把工具定位为“在已确认的当前用户订单上发起指定金额退款”，让描述明确用途、前置条件、单位和错误含义。参数schema约束order_id为字符串、amount为整数分且有范围，禁止多余字段；但服务端还要校验订单存在、归属当前可信身份、可退款状态及余额。负数在无副作用参数检查阶段拒绝，跨用户订单在授权阶段拒绝，所有失败都不能触发支付接口。模型拿到工具描述不代表有执行权限。
工具输出提供稳定status、error_code、retryable、operation_id和最小必要结果；不要塞整份订单和大量日志让模型自行找关键信息。函数调用过程是模型提出调用、应用校验执行、结果按call_id回填、模型解释，不是模型直接运行数据库。可疑参数错误可回传可修正字段，但权限失败不得鼓励猜别人的ID。写工具有幂等键和用户确认绑定，错误响应避免透露他人订单是否真实存在。若供应商支持严格schema可减少结构错误，但具体参数限制仍须核对官方版本，不能把strict当业务安全保证。测试让模型输出负数、超余额、未知字段和合法结构越权，观察执行计数为零；成功时记录操作ID以便追查。替代方案是模型只选择退款意图，确定性UI收集金额和授权，复杂度更低且业务边界更强。

### 关键点

- 工具用途单位和前置条件
- schema后仍业务授权
- call_id回填
- 高信号最小返回

### 可接受替代

- 模型选意图、确定性表单收参数适合高风险写操作
- 只读退款资格工具与写退款工具分开更容易控制

### 常见错误

- 工具描述说“安全退款”就可执行
  - 原因：工具描述说“安全退款”就可执行：名称与描述不能替代真实身份和余额检查。

### 未运行示例

```json
{"status":"rejected","code":"INVALID_AMOUNT","retryable":false,"call_id":"c3","operation_id":null}
```

## Q05 执行循环与终止

假设Agent最多8步、总预算20秒，只能只读搜索；连续三次同一查询空结果。报销流程固定“提取→核对→草稿”，是否需要自由Agent？

### 最低合格

workflow固定路径与Agent动态决策；步数/时间/重复上限；观察回填和完成条件

### 完整参考解法

我会先判断任务路径是否真的需要模型动态规划。固定报销流程可用workflow：代码规定提取、字段验证、规则核对和生成草稿，模型只负责适合语言处理的步骤，失败进入已定义分支。如果用户目标开放，需要模型决定搜什么、根据结果改变方向，才使用有工具的Agent循环。两者都不是越自由越先进，可靠性、费用和可解释性比名称重要。
对搜索Agent，执行层记录当前状态、工具调用与观察，限制最多8步和20秒总预算；每轮完整工具结果按调用ID回填，确认是否有足够证据完成目标。重复三次同一无效查询时不继续付费搜索，尝试一次有理由的改写或停止说明未找到、已尝试范围和需要补什么资料。预算包括工具等待与重试，不只模型生成。终止原因区分成功、无证据、用户取消、错误和上限，不能把到达上限输出的总结当成功。模型提出停止只是一项信号，应用仍按业务完成条件核对，例如必须有适用政策引用。测试给空结果、重复工具、工具超时和伪造成功，检查调用次数不超限及报告不假成功。可以用简单循环实现，不强求LangGraph；若采用框架，要了解它如何终止和恢复。面试证据是清晰状态迁移与失败结果，而非画一个模型不断“反思”的无限环。

### 关键点

- workflow固定路径与Agent动态决策
- 步数/时间/重复上限
- 观察回填和完成条件
- 停止不等于成功

### 可接受替代

- 纯workflow可覆盖稳定业务，少一次规划调用
- 开放检索可用动态Agent，但工具与预算必须限界

### 常见错误

- 再搜直到模型满意
  - 原因：再搜直到模型满意：会重复空查询、耗尽预算，且无可核查成功条件。

```
否则：budget/step/repeat check → allowed tool call → observation
stop(reason=no_evidence|budget|cancelled)，不伪造成功。
```

## Q06 规划与重新规划

教学售后助手收到“查询O17并帮我申请退款”。工具有查订单、查政策、创建申请。订单已签收12天且拆封，政策仅允许7天内未拆封自助退货，其余需人工审核。最多6次工具调用，创建申请是写操作。

### 最低合格

先查订单和有效政策；根据结果把自助退款改为人工审核申请或解释不满足条件；写操作前获得对应内容确认，并设置工具预算和终止条件。

### 完整参考解法

先明确用户允许的范围：查询可以直接进行，退款申请是写操作，需要确认具体订单、金额和申请理由。用只读工具取得O17的归属、签收时间、商品状态以及有效政策，给每个观察保留来源和时间。初始计划应是条件化步骤，而不是先生成“查订单、退款成功”后机械执行。

发现12天且拆封后，自助退款分支不成立。执行器把这个观察写入状态，规划器改为解释政策例外、收集人工审核需要的信息；若用户愿意，则生成审核草稿。不要把“申请审核”描述为“保证退款”。计划状态区分未执行、成功、失败和等待确认，每完成一步检查新证据是否推翻剩余步骤。最多6次调用；预算不足就输出已完成部分和下一步，不通过无限重新规划绕开限制。

选择ReAct循环还是计划执行分离取决于任务长度和可审计需求。此案例流程稳定，确定性工作流加有限模型步骤同样合理。规划不是安全边界：权限、字段检查、确认绑定和幂等必须由工具执行层落实。用不符合政策、政策缺失、用户拒绝、工具超时四类测试验证不会误触退款，也不会重复创建申请。

### 关键点

- 基于观察重新规划
- 区分申请与批准
- 工具预算与终止
- 执行层授权检查

### 可接受替代

- 满足题面授权、证据、预算与恢复要求的框架无关实现同样可接受；需解释取舍。

### 常见错误

- 按原计划退款，因为计划已经生成
  - 原因：计划是可修订的假设，不能覆盖政策、权限或用户确认。
